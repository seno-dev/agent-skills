# 開発フロー

- main は本番デプロイブランチ。開発中の仕様の確認に main は使わない。
- カテゴリ A（`pstack.md` のカテゴリ表）の実装は develop から機能ブランチを切って実装する。カテゴリ B と C は develop に直接コミットする。developと機能ブランチはどちらも開発環境にデプロイしてよい。
- develop がないリポジトリでは main から機能ブランチを切る。main への merge は明示の指示があったときだけ。
- 機能ブランチを develop に取り込むときは、通常の merge にする（squash merge はしない）。main は develop を --ff-only でmergeして進め、ユーザーが明示したときだけ行う。main の rebase と、main への直接 squash はしない。
- develop と機能ブランチへの push は、確認なしで行ってよい。
- 指定された作業ブランチの未 push のコミットと、未コミットの変更は、ユーザーが明示したとき以外、捨てない。origin に揃えるための git reset、git checkout、クリーンはしない。ブランチ名が指定と違うときは、合わせにいかず止めて報告する。同じ作業コピー上で、他の作業がすでに足したコミットは、ブランチの先端から外さない。
- 作業ブランチが決まっている変更は、そのブランチに直接載せる。別ブランチは、同時に書く必要があるときだけにし、終わったらすぐに作業ブランチへ戻す。PR は作らない。
- 調整役（このチャットか Grok Bot）は、カテゴリの判断、受け入れ条件つきの指示文、notes の管理を行い、完了を伝える前に結果を自分で確かめる（コミットを見て、録画を見る）。ファイルを 2〜3 個より多く読むこと、コードを書くこと、実行することは、クラウドエージェント、worker、サブエージェントのいずれかに出す。
- ユーザーに確認や操作を頼むときは、毎回、開く画面、押すメニュー、見る項目までの手順を書く。「設定を確認してください」だけにしない。公式や画面で項目が特定できないときは、特定できないと書いてから、分かっている範囲の手順を書く。
- 作業完了後は、末尾に次のステップの案内を表示する。質問への回答でも、次に相手が動けるなら、末尾に次のステップの案内を書く。次のアクションが、エージェントが実行できることの承諾なら、「この配置で実装しますか？」のように質問文にする。
- 実装の完了を伝えるとき、やらなかったものがあれば、項目ごとにその理由を添える。
- レビューで今は直さない項目を挙げるときは、「後で実装」か「実装しない」の2つに分類しそれぞれ箇条書きする。後で実装は、実装する必要があるが、今はやらないもの。理由を書く。実装しないは、最初からスコープ外のもの、または実装しなくても問題ないもの。実装済みで仕様に合うものは、この二つに入れない。
- main への push、本番環境へのデプロイ、外部 API の実行、データの削除など不可逆な操作は、ユーザーが明示的に指示した場合のみ行う。実装・作成指示だけでは実行しない。開発環境へのデプロイは確認不要。
- 元に戻せない操作が要るとき、またはワークアラウンドが必要なときは、中断してユーザーに確認してから実行する。元に戻せる範囲の小さな支障は自分で直し、報告する。
- ユーザーによる手動変更（エージェント外での編集・文言調整・リネーム等）はすべてユーザーが意図したものとして扱う。勝手に元に戻したり「直し」として再変更したりしない。必要な場合のみ確認する。
- コメントとコミットメッセージは日本語で書く。
