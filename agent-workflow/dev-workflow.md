# 開発フロー

- コード確認と実装は、Cursor で直接作業するときはローカル、Grok Bot 経由のときはクラウドエージェントで行う。Cursor でローカルを見られないときはクラウドを使う。
- main は本番デプロイブランチ。開発中の仕様の確認に main は使わない。
- 比較的大規模な実装は develop からブランチを切って実装する。軽微な修正は develop に直接コミットする。developと機能ブランチはどちらも開発環境にデプロイしてよい。
- 機能ブランチを develop に取り込むときは、通常の merge にする（squash merge はしない）。main は develop を --ff-only でmergeして進め、ユーザーが明示したときだけ行う。main の rebase と、main への直接 squash はしない
- develop と機能ブランチへの push は、確認なしで行ってよい。main への push と本番環境へのデプロイは、ユーザーが明示的に指示した場合のみ行う。
- 指定された作業ブランチの未 push のコミットと、未コミットの変更は、ユーザーが明示したとき以外、捨てない。origin に揃えるための git reset、git checkout、クリーンはしない。ブランチ名が指定と違うときは、合わせにいかず止めて報告する。同じ作業コピー上で、他の作業がすでに足したコミットは、ブランチの先端から外さない。
- 作業者のモデルは原則 composer-2.5。複雑な作業は grok-4.7-medium。hardest tasks（複数の境界をまたぐ設計、並行動作、誤りが目立たないアルゴリズム）は grok-4.7-high。xhigh や opus に上げるときは、その前に確認する。設計と判断はこのチャットのモデルのまま。fastモードは使わない。レビュー役と設計役のモデル、間違えたときの損が大きい領域の扱い、検証に落ちたときの上げ方は `pstack.md` に従う。
- Cursor Projects では、既存のworkerにその作業のcheckoutと依存関係が残っていて、使用したいモデルとworkerのモデルが一致し、会話の前提が次作業を誤らせず、同時に触っても衝突しないときに限り、そのworkerに足す。そうでない場合や、複数の画面やデータの境界をまたぐ大規模な新機能の実装では、新しく作る。
- 作業ブランチが決まっている変更は、そのブランチに直接載せる。別ブランチと PR は、同時に書く必要があるときだけにし、終わったらすぐに作業ブランチへ戻す。
- 方針、分担、命名、ルールの文面は、このチャットで答える。コードの所在や外部資料の本文が要るときだけ作業者を出す。
- 調整役（このチャットか Grok Bot）は、規模の判断、受け入れ条件つきの指示文、notes の管理を行い、完了を伝える前に結果を自分で確かめる（コミットを見て、録画を見る）。ファイルを 2〜3 個より多く読むこと、コードを書くこと、実行することは作業者に出す。「X はどこにあるか」のような質問は、composer-2.5 の読むだけの作業者に出す。
- ユーザーに確認や操作を頼むときは、毎回、開く画面、押すメニュー、見る項目までの手順を書く。「設定を確認してください」だけにしない。公式や画面で項目が特定できないときは、特定できないと書いてから、分かっている範囲の手順を書く。
- 作業完了後は、末尾に次のステップの案内を表示する。質問への回答でも、次に相手が動けるなら、末尾に次のステップの案内を書く。次のアクションが、エージェントが実行できることの承諾なら、「この配置で実装しますか？」のように質問文にする。
- 実装の完了を伝えるとき、やらなかったものがあれば、項目ごとにその理由を添える。
- レビューで今は直さない項目を挙げるときは、「後で実装」か「実装しない」の2つに分類しそれぞれ箇条書きする。後で実装は、実装する必要があるが、今はやらないもの。理由を書く。実装しないは、最初からスコープ外のもの、または実装しなくても問題ないもの。実装済みで仕様に合うものは、この二つに入れない。
- 本番環境へのデプロイ、外部 API の実行、データの削除など不可逆な操作は、ユーザーが明示的に指示した場合のみ行う。実装・作成指示だけでは実行しない。開発環境へのデプロイは確認不要。
- migration の適用状態を保存する先が定義されており、接続先が開発環境だと判定できるとき、次の localhost 確認が migration 後の保存データを読むなら、migration を確認の前に一度実行する。localhost 確認がそのデータを読まないとき、または localhost 確認をせずに開発環境へデプロイするときは、デプロイの前に一度実行する。成功したあとだけ適用状態を更新し、適用済みは再実行しない。判定できないときと本番は自動実行しない。
- 指示された作業に支障がある場合は必ず中断し、ワークアラウンドが必要な場合は必ずユーザーに確認してから実行。
- ユーザーによる手動変更（エージェント外での編集・文言調整・リネーム等）はすべてユーザーが意図したものとして扱う。勝手に元に戻したり「直し」として再変更したりしない。必要な場合のみ確認する。
