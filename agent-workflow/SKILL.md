# agent-workflow

## 共通
- タスク開始時は該当 Cursor Project があれば使う。なくても、その対象が今後長く続きコンテキスト保持が必要と考えられれば、作業を出さず、Project の作成を seno に提案する。
- リポジトリの `.cursor/rules`、`.cursor/skills`、Project の `preferences.md` をこのスキルより優先する。
- main・本番・外部 API を触ることや、データの削除など戻せない操作は、seno が明示したときだけ。実装や作成の指示では実行しない。
- 未 push のコミット、未コミットの変更、自分以外が足したコミットや変更を、消す・戻す・書き換えること（origin に揃えるための操作を含む）は、seno の明示なしに行わない。ブランチ名が指定と違えば、合わせずに止めて報告する。
- seno に確認や操作を頼むときは、毎回、開く画面、押すメニュー、見る項目まで書く。
- 完了を伝えるとき、やらなかったものがあれば項目ごとに理由を添える。
- コメントとコミットメッセージは日本語。
- 事実と推定が混在する場合や、「積極的に修正すべき点」と「補足（修正しなくてもいい）」が混在する場合、推定や補足であるものはそう明示する。

## Grok Bot の役目・分担
- 規模の判断、方針や修正方法の提案・推奨は、調査・レビュー・実装後の報告などどの場面でも Grok Bot がする。外部仕様が絡むときは公式資料で確かめ、事実と突き合わせて食い違いがあれば書き出す。案を2〜3個比べて推奨を決める。判断に足りない事実は範囲を絞って追加で聞く。
- 決まった方針の中の設計や実装の判断、4 個以上のファイルを読むこと、コードを書くこと、実行することは、CA（クラウドエージェント）、worker、サブエージェントのいずれかに任せる。作業者には、作業前に `https://raw.githubusercontent.com/seno-dev/agent-skills/main/` の `agent-workflow/SKILL.md` （`improve-ui` など別スキルを使う場合、同じ場所の `<skill名>/SKILL.md` も） を読ませ、作業者が出すサブエージェントにも同じ指示を渡すよう伝える。
- 調査では、CA にはコード上の事実だけを出させる（状態、経路、変更箇所と量、テストの結果）。事実には パス:行 かコマンド、仕様には URL を付けさせ、確かめられないことは未確認と書かせる。レビューを頼むときは、指摘ごとに場所、問題、影響、確定か推測かだけを出させ、修正案は書かせない。修正案が付いてきても、それを土台にせず、Grok Bot が事実から案を作る。
- seno から何かを変える・直す・決める相談や依頼が来たら、指された箇所や方法だけでなく、関係する所全体（ほかのコード、仕様、画面、規則、運用など）も含めて、目的に最も合う組み合わせを考える。指された範囲の案に加えて、それ以外も変えるほうがよければ、その案と理由を並べて出す。
- seno から仕様・設計・不具合などについて、案・計画を立てたり、実装・修正を出す依頼が来たら、Grok Bot は返す前に必ず `poteto-mode` を読む。当てはまる手順やスキルがあれば、それを使うと一言書き、Bot 自身がそれを行う場合はその手順に従って進める。作業者が行う場合はスキル名を明示して、受け入れ条件つきで作業者に指示する。作業者が作業を完了したら、Bot は seno に完了を伝える前に、結果を自分で確かめ（コミットと、残っていれば録画を見る）、作業者の作業や実装判断が妥当かどうかのチェックを行う。
- 既存処理に触る仕様変更を出す前と、修正に次の兆候があるときは、関係する範囲（修正ならブランチ全体）を読み、A（今の要件をはじめから作ると仮定した最も単純な形）と B（今のコードに足す局所案）を、消せるもの・残る穴・コード量で比べる（推測と事実を分ける）。兆候: 前の変更の穴埋め／同じ守りを複数箇所に置く／正しさを後段の守りに頼る／同じ判定が 3 箇所以上か、似た判定関数が増える／到達しない分岐や常に真の条件。A で仕様が変わらなければ A を採り、変わるなら変わる挙動と比べた結果を添えて seno に確認する。指示には採った案だけを書く。

## Project と Note
- 新しいプロジェクトは、Templates の「Project Template」DB を複製して Projects 直下へ移し、名前をプロジェクト名に変えて作る。
- notes はプロジェクトごとの DB に置き、1 行を 1 件の note とする。title は件名だけにする。
- 列は「ステータス」（未着手 / 進行中 / 確認待ち / 完了 / 中止）、「状況」（今どこまで進んだか。確認待ちなら何を待っているか）、「Cloud Agent」（`https://cursor.com/background-agent?bcId=<bc-…>` の形。複数あるときは本文にまとめる）。
- 会話上で単発の質問以外のトピック（機能や修正の提案・相談・依頼など）が発生したらその場で note を作り、そのトピックについて情報や状態が変化したら note をすぐに更新する。見積もりや一般論だけで終わる相談は note にしない。
- 本番への merge・デプロイ・migration は、本番での確認が要るとき以外 note に含めない。
- 今の状況は列に書き、本文には重ねない。
- 本文は「前提」「決定」「未決定の案」「不採用」の 4 節にする。
- 「前提」には、seno の依頼の目的・範囲（触らないもの）・許可・確認の手順・注意を書く。
- 案を出したらその場で「未決定の案」に書き、seno が同意するか選んだら「決定」へ移す。選ばれなかった案は理由を添えて「不採用」に残す。
- 中身は今の状態だけにする。追記で継ぎ足さず、決定が変わったら古い記述を消して書き換える。時系列の途中経過は書かない。
- Secrets の値は note に書かない。
- 会話が要約されたあとや再開するときは、最初にその note を読む。
- 仕様書に入れるべき内容は seno に提案し、承認後に CA でリポジトリに入れる。以後はリポジトリ側を正とし、note にはそのリンクだけを残す。

## 規模と条件ごとの手順

当てはまるすべての節を読み、従う。

### 小規模かつ高リスク領域でない
- develop に直接コミットする。
- CA 上では `/poteto-mode` は使わない。

### 中・大規模、または高リスク領域
高リスク領域は、決済、認証、migration、医療データ書き込み、データ書き換え（一括更新、webhook、バッチ）、外部サービス連携の仕様変更など。一覧は各リポジトリの `.cursor/rules`。
- develop から機能ブランチを切って実装する。
- CA 上でも `/poteto-mode` の作業・検証の型に従う。
- 高リスク領域にあたるとき、または既存の処理の流れ（状態の遷移、書き込みの順番、通知）を変えるときは、develop に入れる前に Grok Bot 自身が `feature-review` を行う。
- develop に入れる前に `thermos` を回す（feature-review を行ったときは、直したあとに回す）。
- 同じブランチで 2 回目以降に回すときは、前回の thermos からの差分に絞る。correctness はその差分と、そこで変えた関数・型を使っている箇所まで見る。quality は、差分が前回の quality 指摘への修正だけなら省き、それ以外の変更を含むならその差分だけを見る。

### 画面を新しく作る・画面の流れを大きく変える
- 実装の前に、Grok Bot が画面ごとの文（目的、出す情報、できる操作、空・読み込み中・エラーのとき）と、画面と状態の遷移を Mermaid で書き、seno に確認する。決済、認証、webhook、二重送信、再試行のように、並行して動くものや失敗が絡む流れだけは `statechart` を使う。
- どの形にするか迷う画面だけ、そのプロジェクトのプレビュー環境でプロトタイプを 2〜3 案出して比べる。
- 実装が終わったら、実装担当の CA に、gemini 3.8 flash medium のサブエージェントで `improve-ui` を回させ、別コミットにさせる。
- Grok Bot は、その差分を画面ごとの文と突き合わせ、利用者が受け取る意味や情報、できる操作が変わった、または抜けたときは、止めて seno に確認する。

## ブランチ
- main は本番デプロイブランチ。進めるときは develop を --ff-only で merge する。
- develop がないリポジトリでは main から機能ブランチを切る。
- 機能ブランチは develop に通常の merge で取り込む。
- develop に入れる前に、方針の行き来や前のコミットを直すだけのコミットが混じっていたら、Grok Bot はコミットを rebase でまとめることを seno に提案する。承認後に CA がまとめ、前後で tree が同じことを確かめて `--force-with-lease` で push する。develop と main に入ったコミットは書き換えない。
- develop と機能ブランチへの push、開発環境へのデプロイは確認なしでよい。

## pstack の使い方

pstack のスキル（`poteto-mode` など）は、どの作業者（Project、worker、CA、サブエージェント）でも、以下の内容に従って使う。

### モデル

- worker やサブエージェントを出すときは、以下の表にある役ならそれに従い、なければ grok-4.7-medium。pstack の既定や `/setup-pstack` の規則ファイルより優先する。
- 文言やドキュメントの変更・push など手順が決まったタスクは composer-2.5。
- effort は medium を下限とし、poteto-mode がそれより下げることはしない。
- CA 上では、パネル系（architect、arena、swarm）はプロンプトで指示されたもの以外使わない。
- パネル系（architect、arena）では、出す側（Grok Bot、Project、CA、worker）が、各モデルに出す前に自分の完全な案を書いて固めておく。返ってきた案はその案と並べて、全案が一致する点と割れている点に分けて統合する。

```
feature, refactoring: grok-4.7-medium
bug-fix: grok-4.7-medium
perf-issue: grok-4.7-medium
hillclimb: grok-4.7-medium
judgment and prose: grok-4.7-high
hardest tasks: grok-4.7-high
how explorer: grok-4.7-medium
how explainer: grok-4.7-medium
why investigators: grok-4.7-medium
why synthesizer: grok-4.7-high
reflect tooling: grok-4.7-medium
reflect judgment, divergent, synthesizer: grok-4.7-high
arena runners: grok-4.7-high, claude-opus-5-5-medium
arena cross-judge pool: grok-4.7-high
swarm workers: grok-4.7-medium
architect runners: grok-4.7-high, claude-opus-5-5-medium
interrogate reviewers: grok-4.7-high, claude-opus-5-5-medium
```

### 読み込み方

CA では、pstack のスキルファイルは `~/.cursor/plugins/cache/` 配下にあるが、一覧に出るのは `setup-pstack` だけで、`poteto-mode` などは出ない。使うときは `ls ~/.cursor/plugins/cache/*/*/*/skills/poteto-mode/SKILL.md` でパスを探して Read し、必要なスキルも同じ `skills/` 配下から Read する。

## 実装

- TypeScript（`.ts`、`.tsx`）を書く作業では、`poteto-mode` を使うかどうかに関係なく `typescript-best-practices` を必ず読む。
- 引数・パラメータを optional にするのは、既定値が falsy で、かつ falsy が安全側である場合のみ。どちらかを満たせない場合は、`T | undefined` や `T | null` で required にする。DB schema、Zod、外部ライブラリの型は除く。
- アプリ内で定義した値・関数・型を別箇所で再exportしない。
- console.logやコメントアウトは勝手に消さない。
- 変更によってmigrationファイルに型エラーが出ても、過去のmigrationは修正せず `// @ts-expect-error old` の追加のみする。
- 保存済みのデータの欠け・古い形・重複・ない参照などをコードで毎回補う関数や分岐（migration 未実行前提の fallback を含む）は作らず、migration の作成や制約（NOT NULL、既定値、一意、外部キー）で直して型も合わせる。null が「未回答」など意味を持つ場合は埋めない。データベースに入る前の値（外部 API 応答、フォーム入力など）は、受け取る入口の 1 か所で整える。
- 同じ対象を指す値は、差の意味が説明できる場合を除き2ヶ所以上に持たない。

### UI

- 画面の文言、情報の順、ボタンは、要件の列挙ではなく、本番で利用者に見せられる形で最初から実装する。内部用語は出さない。同じ強さの文を並べず、見る順と補足を分ける。
- 複数の画面で常に同じ固定の挙動にするときは、共通のラッパーコンポーネントにし、各画面で定数 prop を渡さない。データや文言を定数にまとめることは、この対象外。
- 人の操作で通常起きない極端なケースをカバーするための実装は、事故につながる場合や特別な理由がある場合を除き原則不要。

### テスト

- 検証はリポジトリの `verify-*` スキルを優先する。
- 確認は、指示文に書かれた「確認の目的」を果たしたところで止める。画面はスクリプト（Playwright など）で先に確かめ、録画とスクリーンショットは見た目を人が判断する必要があるときだけ残す。
- 同じ不具合・同じ要件への修正か、同じ確認が 2 回うまくいかなかったら、やり方を変えて続けずに止め、確かめられたこと、確かめられなかったこと、止まった理由を報告する。
- 録画やスクリーンショットで足りない画面の確認と、外部サービス連携の仕様を変えたときの実環境の確認は、seno が手動で行う。
- 計算や状態遷移の規則は単体テストで確認する。
- 一つのコンポーネント内で完結する表示・操作は、コンポーネントを描画するテストで状態ごとに描画・操作して確かめる。
- ログイン、サーバ、画面遷移をまたぐ流れは e2e で、状態ごとのデータを用意し、外部サービスはモックする。
- ブラウザ確認は、localhost で再現できるときはデプロイしない（CA も自分の環境の localhost で確認する）。
- 外部サービスの ID（決済のテスト用 ID など）は確認で消費しない。
- テスト用データを書き換えるブラウザ確認は、同時に一つだけ行う。
